## Why this post

The other three posts in this set each describe one memory-corruption bug that Microsoft fixed in the October 2026 Outlook update, recovered from the patch. They all skip the same question: how do you find a four-instruction bounds-check fix inside tens of megabytes of stripped, symbol-free binary that was fully recompiled since last month? This post answers that, as a general technique rather than a story about one bug. It is the part that transfers to the next monthly update, and to any closed-source target that ships periodic patches.

The running example is a mail-client component family, but nothing here is specific to it. The same method applies to any vendor that ships cumulative binary updates without source.

## The shape of the problem

A monthly security update to a large application changes a handful of functions to fix a handful of bugs. If you have the build from before the update and the build from after it, the fixes are the differences between them. That is the whole idea of patch-diffing, and it is simple until the binaries are large, stripped, and rebuilt from scratch every month.

Three things make it hard in practice:

- No symbols. Function boundaries and names are gone, so you cannot line functions up by name. You line them up by behavior.
- Full rebuild. The vendor recompiles the whole product, so the compiler reassigns registers, reorders basic blocks, and relocates everything. Two builds a month apart differ in almost every function even where the logic is identical.
- Scale. A component like a mail client's main executable can hold a hundred thousand functions. A diff that is right but slow is useless.

The craft is separating the few real fixes from the enormous background of rebuild noise.

## Step one: acquire matched builds

You need the last build before the fix and the first build with it. For Click-to-Run Office this means the Office Deployment Tool, which downloads an exact version you name from the content delivery network. Pick the update's build number and its immediate predecessor on the same servicing train, because a train with a single monthly cumulative build gives the cleanest one-step diff. Install each into a disposable virtual machine, snapshot the file set, update, snapshot again, and diff the two snapshots by file version to learn which binaries actually changed. Only those binaries are worth diffing. Everything that did not change can be set aside.

For the October 2026 Outlook update, forty-four binaries changed. The shared Office graphics and text libraries that would have been the noisiest targets did not change at all, which immediately narrowed the work to the mail-specific binaries.

## Step two: pair functions across a rebuild

With no symbols, the first job is to decide which function in the new build corresponds to which function in the old one. Address order is worthless after a rebuild, and a plain text diff of decompiled output is worse than worthless: two independent analyses of the same recompiled function diverge in nearly half their lines from register and block-order churn alone, so a text-hash comparison reports most of the binary as changed and then spends hours pairing the false positives.

The technique that works is to pair functions by what the compiler does not churn: the string literals a function references and the named imported calls it makes. Build an inverted index over those anchors, restricting it to selective anchors that appear in only a few functions, and you get a near-linear pairing that is robust to rebuild. Then suppress the remaining noise with two rules: drop any pair whose bodies are near-identical once normalized, and require a minimum body similarity before accepting a pair at all, so that genuinely rewritten functions fall into a new bucket instead of mispairing.

There is one normalization gotcha that will wreck this if you miss it. Disassemblers glue image addresses into their autogenerated symbol names, so a global referenced as `DAT_1807e0760` in one build is `DAT_1808xxxxx` in the next simply because the image was relocated. If you do not collapse those embedded addresses before comparing, thousands of byte-identical functions look changed. Normalizing them away cut the reported-changed count in one of these binaries from nearly two thousand functions to about thirty. The lesson generalizes: before you trust any similarity score, strip every value that a rebuild rebases, including the ones hiding inside symbol names.

## Step three: the blind spot that hides the best bugs

Anchor pairing tells you which functions changed. The next instinct is to rank the changes by how many strings and imported calls they added or removed, on the theory that a real fix usually adds an error string or a helper call. For some fixes that is true. The double-free fix in this cluster added a safe-string helper and removed the unsafe one, so it stood out.

The most dangerous fixes do not show up that way at all. The common shape of a heap or stack overflow fix is an inline bounds check: an added comparison and conditional branch, `if (n > capacity) fail;`, placed before a copy or an array index. That change adds no string. It calls no new function. Its anchor delta is zero. And because the surrounding function was rebuilt anyway, its similarity score is mediocre, so it sinks into the noise alongside thousands of innocent rebuilt functions. A differ that keys on strings and imported calls is structurally blind to exactly the class of fix you most want to find.

This is worth saying plainly because it is a trap you can fall into without noticing. You can sweep a binary, find only string-visible changes, conclude it is clean, and be wrong, because the heap-overflow fix you were looking for was an inline check the whole time. Two of the three bugs in this set were fixes of precisely this shape.

## Step four: diff at the instruction level

To see inline-check fixes you need a diff that compares behavior at the instruction level and is robust to rebuild relocation, not one that compares strings and call targets. Ghidra's Version Tracking does this. Its correlator chain matches functions across two programs by call-graph position and instruction sequence rather than by address or name, so a function that gained a compare-and-branch guard shows up as changed even when nothing else about it did.

Run it headless, not in the interface, so it scales and scripts. The useful output is not the built-in similarity score, which reads as zero for the reference correlators and is misleading. The useful signal is a direct comparison of the matched functions' instruction mnemonic sequences: an added guard always changes the mnemonic stream, and that change survives rebuild rebasing. Filter out the thunks and the compiler stub pairs so they do not drown the real results.

Three operational problems will stop this cold on a large binary, and all three have fixes:

- The default heap is too small. The automatic matching builds a large association set and runs the headless process out of memory on a multi-megabyte binary. Raise the headless maximum heap well above the default before you start.
- The temporary directory fills. The analysis writes heavily to scratch space, and on a machine whose temp directory is a small in-memory filesystem it dies with no space left partway through. Redirect the temporary directory to real disk with room to spare.
- Out-of-memory looks like a clean result. If the matching aborts on an out-of-memory error, the run can still report zero changed functions, which is indistinguishable from a genuinely clean sweep unless you read the log. Always confirm the matcher actually completed before you believe a negative. A zero that came from a crash is the easiest false negative to talk yourself into.

Validate the whole pipeline on a binary you know is unchanged between the two builds: it should report a large number of matched functions and zero changed, with no false positives. Only then trust its verdicts on the binaries that did change.

## Step five: triage the positive deltas

Version Tracking on a large binary still returns more changed functions than you want to read, because a rebuild reshuffles enough code to create some spurious matches. Rank them. The candidates for a bounds-check fix are the functions that grew: more instructions and at least one more conditional branch in the new build than the old, with a copy, an array index, or an allocation somewhere in the body. A function that added a compare, a branch, and nothing else, sitting in front of a memory operation, is the signature you are hunting.

Read those in both builds, before and after, and ask one question of each: did the new build add a length or bounds check that the old build did not have, in front of a write to attacker-influenced data? Most will be refactors, feature changes, or mispairs. A few will be the fix. Watch for cascading address shifts while you read, where a single size change upstream moves a whole block of later functions by a constant offset and makes the differ report shifted-but-identical functions as new. Before analyzing any function flagged as new, check whether it exists verbatim at a constant offset in the other build.

## Step six: variant hunt and the reachability gate

Finding the fix is not the end. A patched bug is an n-day, already closed. The value of understanding it is that it hands you a pattern, and the same pattern often exists elsewhere, unpatched. Once you have the fix, write down its shape in one sentence, for example, a buffer sized by one length snapshot and written by a different length that can grow inside the loop, then grep every sibling in the family for that shape and read the ones that match. A sibling that moves attacker-influenced data through the same mistake, and did not get the fix, is a live finding.

Two gates decide whether such a sibling is worth anything. The first is the trust boundary: is the data it processes actually attacker-controlled, or is it an internal round-trip that only looks like the vulnerable pattern? A shape that matches the patched bug but sits behind an internal-only data source is not a variant, and chasing it wastes the time the method just saved you. The second is reachability: can the vulnerable path be reached from untrusted input at all, and if so, does it need user interaction? That gate is also what keeps an honest writeup honest, because the difference between a no-interaction and a user-interaction bug is a severity tier, and claiming the higher tier without proving the path is the fastest way to discredit everything else you wrote.

For the October 2026 Outlook cluster, the variant hunts came back empty: the siblings of each patched bug were either already correct or sat behind an internal boundary. That is a legitimate result. The method's payoff is not that every hunt finds a zero-day. It is that a monthly binary update becomes a readable list of concrete bugs and a reusable pattern library for the next one.
